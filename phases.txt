Notification spec (v1, standard)
Channel downloads: low importance, silent. The Phase 0 spike compares this with default importance and no sound for lock-screen prominence.
Title is the filename, text is 42% · 5.2 MB/s · 3 min left, subtext is Chrome · <PC name>.
Progress bar via setProgress, indeterminate when the total is unknown.
Ongoing, CATEGORY_PROGRESS, only-alert-once, public lock-screen visibility with a redacted public version when "hide filenames" is on.
A timeout of about 60–90 s refreshed on each update, as a safety net if the PC disappears.
Multiple downloads: one notification each, up to 3, plus a group summary like "3 downloads · 12 MB/s".
Complete or failed: replace with a normal, non-ongoing notification on a separate channel with its own sound setting.
Handle swipe-away with a delete intent. I believe recent Android versions let users dismiss ongoing notifications from non-foreground-service apps, so don't re-post a dismissed download. Confirm this on your phone in Phase 0.
Material You applies to the app's own UI through dynamic color. The system styles the notification itself.
Phase 0: Spikes (about 3 days)

Goal: settle the unknowns before building.

Tasks

 Scaffold the monorepo (/extension, /server, /android, /deploy, /docs) and an ADR folder
 Extension: poll chrome.downloads.search({state:'in_progress'}) every 2 s and check the service worker stays alive for a 10-minute download (fallback: chrome.alarms)

 Compare channel importance options for lock-screen prominence, and test swiping away an ongoing notification
 Write ADR-0001-spikes.md

Done when: a script running on Cloud Run drives a lock-screen progress notification on your phone.

Phase 1: Sensor and brain, local only (1 week)

Features

The extension tracks all active downloads and posts a batched, timestamped sample every 2 s
Popup with server URL, status and an enable toggle
Server computes percentage (null if the total is unknown), smoothed speed from sample deltas, and ETA
States: starting, downloading, paused, completed, failed, erased

Architecture

Extension modules: poller, api, popup
Server modules: api/, tracker/, schemas, and a Notifier interface with a ConsoleNotifier
docs/protocol.md defines schema v1

Tasks

 Define the schema and POST /v1/samples
 Rewrite the tracker in Python with pytest, covering a stalled download, negative or shrinking values, and a total that changes mid-download
 Poller: start on onCreated, stop when idle, detect paused and interrupted
 Handle onErased and cleanup of completed items
 Build a sample-replay tool for testing

Done when: a real 1 GB download shows correct live speed and ETA in the server console.

Phase 2: Pairing, FCM, Android app and Cloud Run (about 1.5 weeks)

Features

QR pairing: the extension shows a QR code and the phone scans it
Android app with onboarding, camera and notification permissions, and a home screen showing the paired PC, its status and an unpair button
FCM relay producing the standard notification described above
Live on Cloud Run, with a prewarm call when a download starts

Architecture

API: POST /v1/pairings, POST /v1/pairings/{code}/claim, GET /v1/pairings/{id}, DELETE /v1/pairings/{id}, POST /v1/samples, GET /health
PairingStore interface with in-memory (tests) and Firestore implementations
The extension gets a bearer secret at pairing (only its hash is stored). Pairing codes expire quickly, with attempt limits
Cloud Run: unauthenticated at the platform level (the extension can't do IAM auth), max-instances=1, min-instances 0, budget alert
The FCM payload carries seq and sent_at, no collapse key, TTL about 30 s, and onNewToken re-registers

Tasks

 Pairing endpoints and secret handling
 FcmNotifier using firebase-admin
 Android: FCM service, notification channels, QR scanner, home screen in Compose Material 3 with dynamic color
 Extension QR popup and "paired" state
 Dockerfile, Cloud Run deploy script, and deploy/cloudrun.md
 Prewarm and retry with backoff in the extension
 Integration test with a fake FCM client

Done when: a PC download shows a lock-screen progress notification in under about 3 s on a warm server, and the first download after idle still works.

Phase 3: Reliability, polish and Live Update mode (1 week)

Features

Server throttling: at most one push per 2–3 s, but state changes (pause, complete, fail) go out immediately
Out-of-order drop via seq, TTL, and the stale-notification timeout plus a "PC offline" state
Multi-download grouping, and complete, failed and paused notifications
"Hide filenames on lock screen" and dismissal handling
Invalid-token cleanup and token refresh
Settings: notification style (Standard or Live Update on Android 16+), sound on completion
Live Update mode: ongoing plus a promotion request plus the manifest permission, with canPostPromotedNotifications() checked and a graceful fallback to Standard. Downloads are user-initiated and ongoing, but Google's listed examples are navigation, calls, rideshare and delivery, so test whether the system actually promotes it

Tasks

 Per-pairing throttler with unit tests (burst, state-change bypass, ordering)
 Phone-side seq and stale handling
 Extension retry and offline-queue behaviour
 Implement Live Update mode and the style picker
 Measure pushes per hour, p50/p95 latency and battery drain over a long download, and record them in docs/metrics.md

Done when: none of the failure cases (server asleep, phone offline, PC sleeping) leaves a frozen notification.

Phase 5: LAN mode (about 1.5 weeks)

Features

The same server runs on the PC and exposes /v1/ws. The extension posts to http://127.0.0.1:PORT
The phone connects via a QR containing address, port, token and a certificate fingerprint
Auto-select: LAN when reachable, FCM otherwise
Heartbeats and reconnect with backoff, with optional mDNS discovery
Documented limits: phone sleep and client isolation on guest or campus Wi-Fi

Architecture

LanNotifier alongside FcmNotifier
Self-signed TLS with the fingerprint pinned by the phone, because Android blocks cleartext by default and its config can't whitelist private IP ranges
A foreground service on the phone only while a LAN session is active. Check the current time limits for foreground-service types on your target Android version

Tasks

 WebSocket endpoint and session handling
 Certificate generation and OkHttp pinning
 Phone LAN client and transport selector
 LAN QR format and the extension's "local server" setting
 Test with the router's internet disconnected, then write up the limitations

Done when: updates arrive with no internet on the router, and the app falls back to FCM when you leave the network.

Phase 6: Hardening and portfolio (1 week)

Features

Field-level encryption of filenames with a key from the QR. The server only needs bytes, total and state, so full end-to-end encryption doesn't fit this design
Input validation, rate limits and secret rotation
CI for pytest, ruff, Android lint and unit tests, and the extension
Optional Chrome Web Store packaging
README with architecture diagram, a 60-second demo video, and a write-up of metrics and trade-offs

Backlog (after v1): the wavy Material 3 Expressive notification and in-app wavy progress, a qBittorrent or aria2 source, pause or cancel from the phone, iOS Live Activities.
